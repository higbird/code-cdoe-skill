# Claude Code, Codex, and Hermes Agent Integration

## Shared conventions

`SKILL.md` is the skill entry point. See the [README](../README.md) for installation and explicit invocation. `agents/openai.yaml` contains no execution logic and must not be the only place where required rules are defined.

The shared instructions do not depend on Claude-specific dynamic command injection, argument substitution, or subagent fields, or on Codex- or Hermes-specific tools. Each client reads the required resources and uses its available terminal. Installing the skill neither runs analyses nor grants additional permissions.

Distinguish three locations:

- Skill root: the directory containing the loaded `SKILL.md`, used to locate references, examples, and required tools.
- Analysis-stage root: the directory containing `input/`, `output/`, `code.txt`, and `readme.md`. Each set represents a stage with defined inputs, objectives, and outputs that can be run and checked independently. Computation and its diagnostic or result plots may share a stage; downstream analyses requiring independent execution use separate sets.
- Execution environment: the local machine, container, or remote host that runs Python, R, or Bash and determines which paths and dependencies are available.

`input/` contains only actual input data or necessary links. Keep executable code and required execution parameters in `code.txt`. Keep data descriptions, methods and parameter explanations, software and package versions, dependencies, and run instructions in `readme.md`. Do not create `input/src/`, `workflow.json`, `config.json`, or `paths.md` to hold code, configuration, or documentation. `readme.md` is documentation, not machine-readable configuration.

Keep `output/` flat by default and retain only artifacts generated by the stage's script. Do not create `runs/`, state, audit, or log-history directories by default. Repeated runs update the corresponding artifacts; remove this run's staging and recovery copies after success. Handle existing files and required environment metadata according to the preservation and authorization rules in `SKILL.md`; do not delete them merely to simplify the structure.

Use the project's configured Python, conda, or virtual environment first. Otherwise resolve the interpreter from the user's configuration, then PATH. The existing compatibility runner requires Python 3.11+; other analyses use versions appropriate to their stage. R or Bash is needed only when the analysis uses it. Do not hard-code interpreter paths from the developer's machine.

## Reading and execution

Claude Code and Codex: read the required support files from the loaded skill location and access the analysis entry point with the available file and terminal tools. Do not assume the working directory is the skill or stage directory.

Hermes Agent: `skill_view` can load the skill and support files. Successful reading does not prove that the terminal backend can access the same paths. For Docker, SSH, and similar backends, first locate the entry point, inputs, required skill tools, and interpreter on the execution side. If copying is necessary, copy only required skill resources to an authorized, accessible location, outside a new stage's `input/`. Do not upload research data automatically.

All clients use the actual interpreter on the execution side and run `code.txt` from the working directory documented in `readme.md`. The following examples are for a Python-only stage; replace the paths and use the appropriate interpreter for R or Bash.

POSIX shell:

```sh
cd "/path/to/analysis-stage"
"/path/to/python" code.txt
```

PowerShell:

```powershell
Set-Location -LiteralPath 'D:/path/to/analysis-stage'
& 'C:/path/to/python.exe' 'code.txt'
```

Document the environment, versions, and run commands in `readme.md`; do not fill `code.txt` with installation instructions or run records. Follow [environment checks and recovery](environment.md) before execution. Static checks do not replace running the analysis and validating its artifacts.

## Existing workflow compatibility

The configuration, multistage, receipt, and persistent-recovery interfaces in `scripts/analysis_workflow.py` are only for existing workflows whose continued maintenance the user has explicitly authorized. See the [tool reference](tools.md). Its existing `input/workflow.json`, auxiliary source files, and `output/.analysis-state/` are not templates for new four-part stage layouts. Without maintenance authorization, do not automatically integrate, migrate, or delete existing configuration and state.

## Validation and evidence limits

The repository's compatibility-tool tests do not require an Agent client:

```text
python -B -m unittest discover -s <skill>/tests -v
```

Runner tests cover compatibility interfaces, receipts, dependency reruns, and failure recovery. Their existing configuration and state layouts do not define the new stage layout. The new resource-portability tests run `code.txt` directly from different skill installation locations and project paths containing spaces, checking synthetic data and plots, flat outputs, and repeated runs without accumulated history directories. They also cover execution without `agents/openai.yaml`. These tests do not simulate client skill discovery, permissions, or model behavior.

After installation, validate each client:

1. Start a new session, confirm that `code-cdoe-skill` appears in the skill list, invoke it explicitly, and verify the loaded location.
2. Ask the Agent to read `assets/minimal/readme.md` and copy the complete synthetic example to a separate, writable stage directory.
3. Run `code.txt` as documented in the example's `readme.md`. Check the inputs, results, plots, four top-level items, and the roles of input and output contents.
4. Run the example again. Confirm that corresponding artifacts are updated, no `runs/`, state, or run-history directories accumulate, and this run's temporary files are removed.

The example validates synthetic computation and structure, not a real scientific analysis. Without a terminal or required dependencies, provide the checks or edits that are possible and identify what was not executed. Real scientific data, R/Bash environments, and remote backends require separate validation.

The format references are [Claude Code Skills](https://code.claude.com/docs/en/skills), [Codex Skills](https://learn.chatgpt.com/docs/build-skills), and [Hermes Skills](https://hermes-agent.nousresearch.com/docs/user-guide/features/skills/). Format compatibility and passing program tests do not establish end-to-end validation with models in all three clients.

Environment exceptions to the four-part stage layout are limited to existing environment files that must remain in place or new environment-tool metadata explicitly requested by the user. Do not create a lockfile or environment directory for every stage by default. The synthetic Python example has no such metadata and is checked for exactly four top-level items. Resolve Rscript from the project environment, the user's configuration, then PATH; reuse the same interpreter and startup configuration for checks, recovery, and analysis. A fixed interpreter does not fix package libraries. On failure, investigate as described in environment.md and record necessary original evidence in `readme.md`. Successful loading in RStudio does not replace checks in the actual execution environment.
